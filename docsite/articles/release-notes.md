# Release notes

Version 11 is `11.0.0-rc.13`. For moving a 10.x codebase, read [Coming from earlier versions](whats-new-11.md) first; this page lists each release.

## Version 11 release candidates

### Changes since rc.12

The [migration guide](whats-new-11.md) lists each removal with what to call instead.

- **One way per job: the second ways are removed, with no `[Obsolete]` step.** The command shortcut terminals `ToListAsync<T>`, `ToArrayAsync<T>`, `ToImmutableArrayAsync<T>`, `ToHashSetAsync<T>`, `FirstAsync<T>`, `FirstOrDefaultAsync<T>`, `SingleAsync<T>` and `SingleOrDefaultAsync<T>` on a command are gone: call `command.Map<T>().ToListAsync(cancellationToken)` and its siblings. `AsAsyncEnumerable(n, params others)` is gone: pass `[n, ..others]` to the `IEnumerable<int>` overloads. `GetMatchingOrdinals` is gone: `MatchingOrdinals(names, sort).ToArray()`. `ConnectionFactoryToPoolAdapter` is internal: `AsPool()` returns `IDbConnectionPool` (or `IDbConnectionPool<TConnection>`).
- **Channel and Dataflow are rebuilt over `Map<T>()`** and are published with the final 11.0.0, not in a release candidate. Their extensions on readers, commands and `IExecuteReader` are removed: call `Map<T>()` first, then `ToChannelReader`, `ToChannel`, `ToTargetBlock` or `AsSourceBlock`. Channel no longer depends on `Open.ChannelExtensions`.
- **Classic command parameters.** A command built with `Command(...)` on a literal text sizes its parameter list from the `@names` the text declares, and sends an input parameter written without its `@` (or in another case) under the text's own spelling, as a `DbQuery` does. An output, input-output or return-value parameter keeps the name it was added with, so `Parameters["id"]` reads it back. Two spellings of one declared name are sent as written.
- **The raw reader's `ToListAsync(Func<IDataRecord, ValueTask<T>>)` collects into pooled chunks** and copies once into a list of exactly the number of rows, as the mapped terminals do, instead of growing a list.
- **Docs.** New pages: a controller with no service layer, and the same with minimal APIs. The XML documentation of Core and MSSqlClient says what a caller needs and what a streaming member costs; every docsite page, README and sample is cut to what a reader needs, and the README performance figures come from the recorded data.

### Changes since rc.11

The [migration guide](whats-new-11.md) groups the removals by theme, with what to call instead.

- **Everything marked `[Obsolete]` is removed, with the `Results` family and the per-row command terminals that duplicate a `Map` terminal.** `Results<T>`, `ResultsAsync<T>`, `ResultsBuffered<T>`, `ResultsFromDataTable`, `DataTable.To<T>`, the selector forms of `First`, `FirstOrDefault`, `Single`, `SingleOrDefault`, `Take`, `Skip`, `SkipThenTake`, `ToList`, `ToArray` and `ToImmutableArray`, `ExpressiveDbCommandBase.TakeAsync`, `IterateReader*`, `ForEachAsync` on commands, `QueryResultCollection<T>`, `DequeueAs<T>`, the token-first `ReadAsync`, the `bool configureAwait` overloads of `EnsureOpenAsync` and `OpenAsync`, and the protected `ExpressiveCommandBase.Concat<T>` are gone. Call `Map<T>().ToListAsync(cancellationToken)` or `Map(selector)` with the terminal you need; add `.SingleResult()` before `Map` where the old call read only the first result set. Behavior a caller will notice: `Results` and `ResultsAsync` were lazy and `ToList` buffers every row; an empty `DataTable` does not report a missing `required` column (`table.Map(map).ToList()` reports at the first row); `Take(0)` runs the command.
- **Rows without a model: `AsObjectArrays()` and `AsDictionaryRows()`.** They are mapped views like `Map<T>()` (the same terminals, `Skip` and `Take`, `SingleResult()`, `AsyncReads()`, `UsePool`, read-through and pooling) on `IExecuteReader`, `IDbCommand`, `IDataReader`, `DataTable` and the `DbQuery` definition. `DictionaryRow` is a `readonly struct` over one `object?[]` and the column names that every row of the result set shares; `row["Id"]` matches the exact name, else ignoring case, and `row.ToDictionary()` copies. A database NULL is `null`. They replace `Retrieve`, `RetrieveAsync`, `QueryResult<T>`, `QueryResultQueue<T>`, `DequeueAs<T>`, `DequeueAsMappedDictionaries`, `AsMappedDictionaries`, `FirstOrdinalResults` and `FirstOrdinalResultsAsync`, `AsEnumerable(IDataReader, ...)`, `GetValues(IDataRecord, ...)` and `GetValuesFromOrdinals`, which are removed with no `[Obsolete]` step.
- **`Core.Transformer<T>` is removed:** map with `Map<T>()`, or a `RowMap<T>` passed to `Map`. The mapped overloads of the Channel and Dataflow packages rent their row arrays from `ArrayPool<object>.Shared` and clear them on return.
- **The blocking calls are in `Open.Database.Extensions.Synchronous`.** Add `using Open.Database.Extensions.Synchronous;` where the compiler says a blocking call is missing (CS1061, CS1929). Nothing a blocking call does changes. `Execute<T>(f)` and `ExecuteReader<T>(f)` infer `T`, so a call that named `T` alone needs both type arguments or none. A command type of your own has no blocking side: a blocking call throws `NotSupportedException` and the message says to use the async call. The `ExecuteTransaction*` overloads that took the token right after the connection are removed: pass it after the callback.
- **`Stream(stallTimeout, cancellationToken)` is the one unbuffered read.** It is on `MappedQuery<T>`, `MappedQueryWithSkip<T>`, `MappedQueryWithTake<T>` and `MappedCommand<T>` and returns an `IAsyncEnumerable<T>`: lazy, enumerated once. The timeout is required: the longest the consumer may go without pulling the next row. A stalled consumer stops the read, cancels the command, closes the connection the library opened and gets a `TimeoutException` on its next pull; `Timeout.InfiniteTimeSpan` accepts an unbounded hold. It replaces `Read`, `Read<TResult>`, `ReadAsync` and `ReadAsync<TResult>` on those four views. `IMappedQuery<T>` has two members, `ToAsyncBufferStream` and `Stream`; its extension terminals are gone (call the terminal on the view), and the `IExecuteReaderSync`, `IExecuteCommandSync` and `IMappedQuerySync<T>` interfaces are not public. `MappedReader<T>` and `MappedTable<T>` keep their own `Read` and `ReadAsync`.
- **The cancellation token can be passed positionally.** Every terminal with an optional comparer, command behavior or flag has an overload that ends in `CancellationToken cancellationToken = default`: `await query.ToDictionaryAsync(post => post.Id, cancellationToken)`. The comparer or behavior on the original member is required (source-level only; compiled callers are unaffected). A bare `default` in that slot binds the token overload: `reader.ForEachAsync(handler, default)` reads with `ReadAsync`, where it bound the flag (`false`, synchronous reads) before. Pass `false` to keep synchronous reads.
- **`DbQuery` takes `Map<T>()` on the definition.** `DbQuery.Text(sql).Map<Post>()` (also `Map(RowMap<T>)` and `Map(selector)`, and the same on `DbQuery<TParams>`) is an immutable `MappedDbQuery<T>`: the map and its compiled reader live with the definition. `Using(connection | transaction | pool | factory)` returns the mapped view, and parameters go before or after `Using` with the same command either way. `PooledBuffer<T>.From(rows)` makes a finished buffer from rows you already have. A read that finds no rows completes `Items` with the shared `PooledArray<T>.Empty`, which keeps working after the buffer is disposed.
- **Decorated models are hard instructions.** `[Column(Name)]`, `[Column(Order = n)]` and `[NotMapped]` on a model are honored by the runtime map: a declared column that is missing, or not at its declared ordinal, throws `ValueMappingException` (checked once per result set, nothing per row); a declared name matches exactly or ignoring case, never by inference; `[NotMapped]` members are never read; contradictions throw `InvalidOperationException` at the call; a `RowMap<T>` pair on a member overrides its declarations.
- **The pool hand-off is by bytes.** A released chunk is cleared by the recycle bin from 128 KB of rows (rows times row size), value rows included; a smaller one is cleared in place.
- **Null arguments are refused with `ArgumentNullException`,** thrown at the call, for `IDbConnection.OpenAsync`, `AsPool`, the `Func` connection-source `Command` and `StoredProcedure` extensions, `ReadAsync` and the `DataRecord` ordinal helpers. A connection that reported `Open | Broken` is closed again after a transaction call, and the transaction `CreateCommand` extensions dispose the command if the provider refuses the transaction.
- **`DbQueryCall` is a `readonly struct`.** `DbQueryCall?` is `Nullable<DbQueryCall>`, so `== null` no longer compiles. A parameter name written by hand that the SQL text declares (with or without `@`, any case) is sent as the text writes it (`@name`); an undeclared name is sent as written; procedures are unchanged.
- **`Open.Database.Extensions.SqlClient` (System.Data.SqlClient) is not published for version 11.** Use `Open.Database.Extensions.MSSqlClient` (Microsoft.Data.SqlClient). The Channel and Dataflow packages are published with the final 11.0.0.
- **Docs and benchmarks.** The XML documentation of Core and MSSqlClient is rewritten; the `DictionaryRow` remarks say which reads allocate nothing; the pooling page has the bin proof; the library comparison is a newer run; the two LocalDB benchmark classes are gone and the SQL Server benchmark databases keep their files in the scratch folder.

### Changes since rc.10

- **A query can be defined once and bound where it runs: `DbQuery`.** `DbQuery.Text(sql)` and `DbQuery.Procedure(name)` make an immutable definition (a static field is the natural home); `Using(connection | transaction | pool | factory)` binds it to wherever it runs, and each `AddParam` returns a new immutable call. `Params<T>()` declares a struct of values the compiler checks. Parameter names are resolved as a command resolves them. The connection is opened late and closed only when the call opened it (closed or broken); a factory's connection is disposed and a pool's is given back even when the run throws; a transaction's connection is never opened or closed. See [Expressive commands](expressive-commands.md).
- **Pooled arrays follow one clearing rule.** Rows that hold references are always cleared before their array goes back to the pool; nothing turns that off. Rows without references are cleared only when you ask: per query with `clearOnReturn: true`, or for the whole app with the switch `Open.Database.Extensions.ClearPooledArrays`. Only the rows that were written are cleared, and a chunk of 128 KB or more of rows is cleared off the read path. See [Async buffers and streams](async-buffers.md#pooled-memory).
- **New: `.UsePool(ArrayPool<T> pool, bool clearOnReturn)` after `Map`** chooses the pool and the clearing for one query; both arguments are required, and every pooling terminal (`ToListAsync`, `ToArrayAsync`, `ToImmutableArrayAsync`, `ToHashSetAsync`, `ToDictionaryAsync`, the buffers and streams) rents from it. An explicit `clearOnReturn: false` wins over the app-wide switch for that query, except for reference rows. Used through the `IMappedQuery<T>` interface it is honoured the same way; a query that is not ODX's own is collected without pooling.
- **Removed: the flag and pool overloads of `ToAsyncBuffer`, `ToAsyncBufferStream` and `ToBufferedAsyncStream`** (`clearOnDispose` / `clearOnReturn` and `MemoryPool<T>`). Each now takes only a cancellation token: `query.UsePool(pool, clearOnReturn: true).ToAsyncBuffer(cancellationToken)` replaces `query.ToAsyncBuffer(pool, true, cancellationToken)`.
- **New: `ConnectionScope<TConnection>`, with `EnsureOpenScope` and `EnsureOpenScopeAsync`** on a connection, a connection factory and a connection pool. The scope opens the connection if it needs it and, when disposed, lets go of it the way its source calls for: a connection you already hold is closed again if the scope opened it (never disposed), a factory's connection is disposed, a pool's is given back. `await using var _ = await connection.EnsureOpenScopeAsync(cancellationToken);` replaces the open-and-close `try`/`finally`; `scope.Connection` and `scope.PriorState` give the connection and the state it was found in, and `scope.ReaderBehavior()` adds `CommandBehavior.CloseConnection` when the scope opened the connection. The `Open`, `OpenAsync`, `Using` and `UsingAsync` callbacks of a factory or a pool are built on it, so the asynchronous factory callbacks now dispose with `DisposeAsync`.
- **A broken connection is closed again afterwards, and one that is not a `DbConnection` is not leaked.** The checks that decide whether a command closes a connection it opened share one definition (closed, connecting or broken). A `DbQuery` factory or pool that supplies something that is not a `DbConnection` has it disposed or given back, and the run throws `InvalidOperationException` naming the type.
- **Docs.** The benchmarks pages: one per exploration and one shared page for the method.

### Changes since rc.9
- **`ToListAsync`, `ToArrayAsync`, `ToImmutableArrayAsync`, `ToHashSetAsync` and `ToDictionaryAsync` build an exactly sized result, once.** A list or array used to grow while the reader was open (doubling, so a 10,000-row list kept room for 16,384). The rows now go into a chain of pooled chunks on the calling flow, with no background producer, and the result is built right after the last row: one block copy for a list, an array or an immutable array, and a hash set or dictionary created at the size of the result, so it never regrows. `ToImmutableArrayAsync` wraps the array without a copy on .NET 8 and later. The synchronous `ToHashSet` and `ToDictionary` work the same way. In the library's synthetic benchmark, 10,000 rows into `ToListAsync` take 206 µs, against 522 µs in rc.9; with a 50 µs network link every route is within 3%, so expect less time on the CPU and less garbage, not a faster query. Bytes per call against SQL Server LocalDB are at most 16 B above rc.9 for 1 and 100 rows, and 1,320 B below it for a 100-row list. One change you can see: a duplicate or null key in `ToDictionary` and `ToDictionaryAsync` throws the same exception as before, but only after every row has been read, and the key and value selectors run after the read. New: `PooledArray<T>.ToArray()` and `ToList()` copy a buffer's rows into an exactly sized array or list.

- **Derived parameter names allocate no more than explicit ones when the SQL text is built at run time, and nothing is stored for such a text.** The `@name` markers of a text command were remembered per string object, so a text assembled on every call was parsed again on every call and left an entry behind: 680 B more per call for one parameter, 1,360 B for four. Now only a literal or `const` text (an interned string) is parsed once and remembered. Any other text is matched by a scan that allocates nothing and stores nothing, so a rebuilt text costs within 16 B of naming the parameters yourself. The price is CPU time: the scan runs on every call, and it grows with the length of the text and the number of parameters. In a single-threaded benchmark it took about 0.5 µs for a 200-character text with one parameter and about 20 µs for a 2,000-character text with four. A `static readonly` text that is built at startup is not interned either, so it is scanned on every call too. Where that matters, keep the SQL in a literal or `const`, or name the parameters. No API changes.

- **An unreadable procedure is looked up once in 15 seconds, not once per run, and a stale list no longer outlives an empty answer.** When the provider reported no parameter names for a stored procedure (the login cannot see it, it does not exist, or it declares no parameters), nothing was remembered, so every run read the names again: one extra schema query per execute while the connection was open. And when such an answer came after an older list, the older list stayed for the full five minutes, so a procedure that had lost its parameters was still sent the old ones. An empty answer now replaces the older list and is remembered for 15 seconds (a fraction of the five minutes for known names, so a procedure that is created or changed shows up soon). Derived names are sent as written until then. No API changes.

- **A parameter added to a stored procedure is no longer silently left out of an `AddParams` call.** `AddParams(new { Id, Title })` against a procedure that declared only `@Id` remembered those names, and when the procedure later gained `@Title` (inside the five minutes the names are remembered), the run dropped `Title` with no error and the procedure used its default. A member that the remembered names do not declare now makes the library read the names once more before it drops the member, as an unmatched `AddParam(value)` argument already did. If the second read still lacks the member it is dropped as before, and that read is remembered, so a member the procedure never takes costs one extra read per five minutes, not one per run (a procedure that declares no parameters: every 15 seconds, see above). No signatures change. See [Remembered names](expressive-commands.md#remembered-names).

- **A mapped read no longer boxes a date, a decimal or a bool that the provider hands over as another type.** SQLite stores a date and a decimal as text and a bool as an integer, so the column type differs from the member type, and each such cell cost a box on top of the value: 24 bytes for a `DateTime`, 32 for a `decimal`, 48 for a `bool`, per row (the nullable members too). The map now reads them through a typed conversion with the same culture, the same failures and the same NULL rules as before, and allocates what the hand-written read does. No signatures change.

- **Docs.** A "Start here" at the top of the what-is-new page. New articles: [Shaping rows](shaping-rows.md) and [How little code](how-little-code.md) (the same four tasks with ODX, Dapper, EF Core and ADO.NET). The streaming members are documented as not the recommended way to read rows, because they hold the connection for every row. [Async buffers and streams](async-buffers.md) covers who owns a `PooledBuffer` and for how long, including returning one from a controller. [Mapping](mapping.md) shows how to get an immutable or frozen result from the terminals.

### Changes since rc.8

- **A NULL passed to a typed `AddParam` overload is now sent with that type.** `AddParam("@id", (long?)null)`, `AddParam("@x", default(int?))` and `AddParam("@s", (string?)null)` (and the same forms of `AddParamIf`) used to send the NULL with no database type, so the provider chose its own default. A consumer reported that as a different parameter type, an implicit conversion and a different query plan on SQL Server. The parameter now takes the database type of the overload's static type, the same mapping `AddParams` already used for a NULL member. A database type you pass always wins, and a value is left to the provider as before. Two things to know: a bare `AddParam("@a", null)` literal binds the `string?` overload, so it is now sent as a `String` NULL; and a value of type `object`, or a call that gives the direction by position (`AddParam(name, value, ParameterDirection.Input)`), has no type to use, so pass a database type or write `direction: ...`. No signatures change.

### Changes since rc.7

- **New: `ToAsyncBuffer`, `ToAsyncBufferStream` and `ToBufferedAsyncStream` on the typed views** (what `Map<T>()` returns, with `Skip` and `Take`). Each reads the query on its own background producer into pooled chunks, so the connection is released as soon as the last row is read, however slowly the consumer works. `ToAsyncBuffer` starts the read at the call and returns a `PooledBuffer<T>` that you can hand to another layer (a controller, say) and read later: `await buffer.Items` gives a `PooledArray<T>`, a read-only list with an O(1) indexer that LINQ copies quickly. Disposing the buffer returns the arrays to the pool, and cancels the query if it is still running. `ToAsyncBufferStream` is a lazy, single-use `IAsyncEnumerable<ReadOnlyMemory<T>>` of chunks, and `ToBufferedAsyncStream` is the same stream element by element. Each took a `clearOnDispose` or `clearOnReturn` flag and optionally a `MemoryPool<T>`; in rc.11 they take only a cancellation token, and the pool and the clearing are chosen once with `.UsePool(ArrayPool<T> pool, bool clearOnReturn)` after `Map` (see "Changes since rc.10"). Rows that hold references are always cleared before their array goes back; rows without references only when you ask. See [Async buffers and streams](async-buffers.md).
- **Clearing a large chunk is done off the read path, and bounded.** (Changed in rc.12: see "Changes since rc.11".) A chunk of rows that hold references and is 4,096 rows or more is cleared on one background loop; a smaller one is cleared where it is released. If the loop cannot take a chunk (it is behind, or it throws), the chunk is cleared where it is released instead: nothing is skipped, left dirty or lost. See [Pooled memory](async-buffers.md#pooled-memory).
- **Removed: `ToChannelReader` and `ToChannel` on the typed views** (what `Map<T>()` returns, with `Skip` and `Take`): 48 signatures in all. A call to one no longer compiles. They are planned to come back in the Channel library. To read a query while a consumer works, use `ToBufferedAsyncStream` (the elements) or `ToAsyncBufferStream` (the chunks): the query is read on a background producer and the connection is released as soon as the last row is read. For a projection after the map, use `System.Linq.Async` over the stream. The row count that `ToChannel(out Task<long> readCount, ...)` returned has no replacement: count the rows as you read them, or read `Items.Count` of a buffer. See [Channels and Dataflow](channels-and-dataflow.md). The `ToChannel` overloads of the Channel library, on a command or a reader, are not affected.

### Changes since rc.6

- **A cancel that cuts a reader-level read short now throws `OperationCanceledException`.** `ForEach`, `IterateWhile`, `Select` and `SelectAsync` on a reader, their async forms, and the reader-level `ToChannel` overloads that take a transform used to end quietly by default and return a partial result that looked complete. They now check the token at the top of the loop, before each read, and the async forms hand it to `ReadAsync` and `NextResultAsync`, so the provider cancels the read itself. A read that already returned its last row is complete: a cancel after that is not an error. **Removed:** the `throwOnCancellation` parameter on `ForEach`, `IterateWhile`, `Select` and `SelectAsync`, six signatures in all. A call that passed it no longer compiles (CS1503 or CS1501): delete the argument, as in `Select(reader, transform, cancellationToken)`. To stop early without an exception, return `false` from the predicate or leave the loop. A mapped query over a plain `IDataReader` now forwards the token, so a cancel between rows throws.
- **`AddParam` and `AddParamIf` take an `object?` value** in the `(name, value, type, direction)` forms, so a typed NULL such as `AddParam(name, (byte[]?)null, SqlDbType.VarBinary)` compiles without a nullability warning and sends `DBNull`. No existing call changes.
- **A stored procedure's parameter names are resolved on every run.** A command that gets its names from the database (`AddParam(value)` with no name) used to resolve them once and write them into `Params`, so a second run of the same command object, after a change of connection, database or procedure, could send the first run's names. The names are now resolved on every run into a list of their own, and `Params` keeps what you added. No API changes. One visible change: after a run, `Params` shows what you added, not the resolved names. To see what was sent, read the provider command's `Parameters` in `Execute(command => ...)`.
- **Documentation:** a new [AsyncReads()](async-reads.md) page says why rows are read with `Read()` by default, what the opt-in costs and when to use it. The [Performance](performance.md) page now leads with ranked charts, with their data tables and CSVs in [Performance data](performance-data.md), and the same charts are on a [benchmark charts](../benchmarks/ranking.html) page. The Core README has a section on trimming and native AOT, with a recipe for a trimmed app (see "Known limitations"). The examples in the README, the mapping article, the samples and the XML documentation use async terminals with a real `CancellationToken`, `static` lambdas and one pair per line.

### Changes since rc.5

- **Rows are read with `Read()` by default, on async terminals too.** `ToListAsync`, `FirstOrDefaultAsync` and the other async terminals still execute the command and open the connection asynchronously, but they read the rows with `Read()`. On the measured runs a synchronous row read costs less CPU, and about 40% less memory on the `Map(Func)` path, for the same wall time over a real network link. To read the rows with `ReadAsync()`, for a caller whose thread must not block while rows arrive, call `AsyncReads()`: `cmd.AsyncReads().Map<T>()`, or `dbCommand.Map<T>().AsyncReads()`. **Removed, with no bridge:** `EnableAsyncRead(bool)` and the `UseAsyncRead` property. Replace `EnableAsyncRead()` with `AsyncReads()`. A plain `IDataReader` read by an async terminal now checks the cancellation token on every row.
- **`RowMap<T>.From(factory, pairs)` builds a map from a delegate**, such as a lambda, a method group or a constructor wrapper. Its parameters bind to columns by the rules a constructor already uses: a pair renames a parameter to a column, then columns match by name, ignoring case. A missing or `NULL` value in a non-nullable parameter gets the parameter's declared default, else `default`. Declare the map once:

  ```cs
  static readonly RowMap<PostSummary> Summary = RowMap<PostSummary>.From(
  	static (int id, string title) => new PostSummary(id, title));

  List<PostSummary> posts = await cmd
  	.Map(Summary)
  	.ToListAsync(cancellationToken);
  ```

  On C# 12 the pairs argument must be written out. A single target-typed `new(...)` as the only pair does not compile: write the element type.
- **The `Map<T>(pair...)` overloads are removed.** There is one way to pass pairs: a `RowMap<T>`, declared once and passed to `Map`. A one-off is `Map(new RowMap<T>(pair, pair))`. `Map<T>([...])`, with a collection expression, still compiles: it converts to a `RowMap<T>`. One behavior change comes with it, with no compile error: `Map<int>([])` now throws (see [Coming from earlier versions](whats-new-11.md)).
- **`Select(selector)` on an `IMappedQuery<T>`, added in rc.5, is removed:** it built a second object for every row while the reader was open. Shape each row into the result type with `Map(RowMap<TResult>.From(factory))` instead. A data class can return that mapped query and let each caller choose the terminal. The reader-level `Select` is unchanged.
- **Fix:** the async terminals on an `IMappedQuery<T>` that this library did not build (your own implementation) no longer resume on the caller's synchronization context.
- **Fix:** an `AddParams` member that the procedure, or the command text, does not declare is no longer sent under a stale name left in a shared pool.
- A package built in a Release build no longer carries the build machine's folder names: the SDK's `DeterministicSourcePaths` maps the repository folder to a neutral prefix in the dll, the debug symbols and the Source Link mapping.

### Changes since rc.4

- Version 11 targets .NET 11: every package adds `net11.0` next to `net10.0` (LTS), `netstandard2.0` and `netstandard2.1` (`MSSqlClient`: `net472`, `net10.0` and `net11.0`). Each major version of the library targets the matching .NET. Building the repository needs the .NET 11 SDK (`global.json`).
- `.SingleResult()` can be written before `Map`, so a query reads as behavior first, then shape: `command.SingleResult().Map<Post>().ToListAsync(cancellationToken)`. It works on an expressive command (`IExecuteReader`) and on a raw `IDbCommand` or `DbCommand`, with the same `Map` overloads as before, and it is the same as `command.Map<Post>().SingleResult()`, which still works. There is none on `IDataReader` or `DataTable`: their views never read through, so there is nothing to opt out of. Nothing changes by default: without it a `Map` terminal still reads through the later result sets.
- **`ExecuteScalar<T>()` and `ExecuteScalarAsync<T>()` convert the way `Map<T>()` does.** They cast the provider's value exactly, so a `bigint` read as `int`, or a `numeric` read as `long`, threw `InvalidCastException`, which a port from Dapper met only on a real database. Now a value that is already a `T` is returned as it is, an integer converts to another integer type with a range check, and any other value is converted by the same code `Map<T>()` uses. `NULL` and no row still give `default(T)`. A value that cannot be converted, or does not fit, throws `ValueMappingException` with the conversion's error inside. **Behavior change:** a call that threw `InvalidCastException` now converts, or throws that exception. `ExecuteReturn<T>()` and `ExecuteReturnAsync<T>()` convert the same way. The overloads that take a `Func<object?, T>` are unchanged.
- A `RowMap<T>` takes a converter for a column that needs a trim, a parse or a format on its way to a member: `map.Convert<long, string>(nameof(Order.OrderNum), n => n.ToString("D6"))`, or `Convert<TColumn, TMember>(member, column, convert)` to name the column as well. It returns a new map, and the delegate runs inside the compiled row reader, so a result maps straight into the type you want, with no row type to copy from. A converter is not called for a NULL cell (the member follows the NULL rules); a `Nullable<>` `TColumn` is called with null. See [Converting a column](mapping.md#converting-a-column).
- `First()` and `Single()` (and `FirstAsync(cancellationToken)`, `SingleAsync(cancellationToken)`) on `Map<T>()` throw `InvalidOperationException` when the query returns no row, and `Single` also when it returns more than one. An insert that returns its new id is one `await command.Map<long>().SingleAsync(cancellationToken)`, with no handler to check the row count. The commands have the shortcuts too: `command.SingleAsync<long>(cancellationToken)`. A `NULL` value is still a row. The error for no rows is thrown after the connection is released and the later result sets are read, so a failure in one of them comes first. See [Terminals](mapping.md#terminals).
- `ToDictionary` and `ToDictionaryAsync` on `Map<T>()` take a value selector: `ToDictionaryAsync(post => post.Id, post => post.Body ?? "")` builds the lookup in one pass, without keeping the rows. A duplicate key throws, as it does without the value selector.

### Breaking in rc.4

Rebuild consumers of rc.3. Both changes are source-compatible for every call except the ones noted.

- `ExpressiveDbCommand.RetrieveAsync` takes a trailing `CancellationToken cancellationToken = default` on the three overloads that can: `RetrieveAsync(CancellationToken)`, `RetrieveAsync(IEnumerable<int>, CancellationToken)` and `RetrieveAsync(IEnumerable<string>, bool, CancellationToken)`. The token is used together with the command's own token. A `params` list must come last, so the two `params` overloads (`RetrieveAsync(int, params IEnumerable<int>)` and `RetrieveAsync(string, params IEnumerable<string>)`) are unchanged and take no token: pass the ordinals or names as a collection to the `IEnumerable` overload to cancel. A call that passed no token binds to the same overload as before, but the signatures are new, so rebuild.
- Three parameters are renamed to say what they hold. This breaks only a caller that passes the argument by name: `CreateTextCommand(SqlTransaction, ...)` in `SqlClient` and `MSSqlClient` takes `commandText` (it was `procedureName`), `CreateStoredProcedureCommand(IDbConnection, ...)` in Core takes `procedureName` (it was `commandText`), and the type parameter `TConn` of the `Using` and `UsingAsync` connection helpers is now `TConnection`. The type-parameter rename breaks no caller.

### Changes since rc.3

- The asynchronous terminals on a command take the element type: `await command.ToArrayAsync<int>(cancellationToken)` is `Map<int>()` then the terminal. `Map<T>()` of a single value such as `int` reads the first column.
- `reader.Map<T>()` and `command.Map<T>()` map a plain `IDataReader` or `IDbCommand` with the same terminals as an expressive command's `Map<T>()`. The reader is never opened, closed, disposed or advanced to the next result set; a command opens and closes only the connection it opened. See [Mapping a reader or a command you already have](mapping.md#mapping-a-reader-or-a-command-you-already-have).
- `table.Map<T>()` maps a DataTable you already have (a `MappedTable<T>`; each terminal reads through its own DataTableReader).
- A null `RowMap<T>` passed to `Map<T>(map)` no longer throws `ArgumentNullException`: it maps exactly as `Map<T>()` does (a single value reads the first column).
- A type of your own that implements both `IExecuteReader` and `IDbCommand` (or `IDataReader`) now gets an ambiguous `Map` call (CS0121); cast it to the interface you mean.
- A `default` `MappedQuery<T>` (or `MappedQueryWithSkip<T>`, `MappedQueryWithTake<T>`) now throws `InvalidOperationException` when used, where it threw `NullReferenceException`.
- Members with a better route are marked `[Obsolete]`. Each message names the replacement, and they are removed in rc.12. They are warnings, never errors, but a build that treats warnings as errors stops on them until you move to the replacement or suppress `CS0618`.
- The asynchronous command paths dispose their reader with `ConfigureAwait(false)` on `netstandard2.1`, `net10.0` and `net11.0`.
- The `Map<T>` documentation now says how columns match by default: exactly, else ignoring case, else ignoring case and underscores (`author_id` feeds `AuthorId`).

### Changes since rc.2

- A `Map` terminal now reads through the later result sets after the first, so a failure in a later statement is thrown, where rc.2 returned the rows and lost it. This is a behavior change from rc.2. `Map` still returns only the first set's rows. `.SingleResult()` after `Map` stops after the first set and does not see a later failure. A later failure can follow a write that already committed, so a caller that retries can repeat it. The older command methods, Channel and Dataflow do not read through yet.
- `ToDataTable` now reads one result set and leaves the reader on it, so `NextResult` works after it. A second `ToDataTable` call in a row returns no rows, because the reader is still on that set and its rows are already read. A loop on `while (!reader.IsClosed)` around `ToDataTable` no longer ends: use `NextResult`. `ToDataTables` returns one table per result set.
- A connection the library opened is closed when the provider fails to start a reader, in Core and in the two SQL Server packages.
- `EnsureOpenAsync` and `OpenAsync` always use `ConfigureAwait(false)`. The overloads with a `bool configureAwait` are obsolete and ignore it (removed in rc.12).
- A null collection is treated as empty, and a null reader or selector is checked once.

### Changes since rc.1

- Generic commands (`ExpressiveCommand`, `ExpressiveDbCommand`) send each parameter's direction, so output parameters work.
- `AddParam(name, DbType, direction)` works on the SQL Server commands.
- `AddParams(x)` with `x` typed `object` sends the members of its real type.
- `AddParam(value)` finds a stored procedure's parameter names through the `ProcedureParameters` schema on any `DbConnection`.
- On a text command, `AddParam(value)` and `AddParams(object)` use the `@name` markers in the SQL.
- `Map<T>()` on a dictionary or `ExpandoObject` throws, where it used to return empty rows.

### Fixes in 11.0, since 10.1.0

- **`ExecuteReturn<T>()` and `ExecuteReturnAsync<T>()`** return `default(T)` for a NULL return value instead of throwing `NullReferenceException` for a value type.
- **Channels and Dataflow.** With `complete: false`, the command no longer runs twice. The mapped `ToChannel<T>`, `ToChannelAsync<T>` and `ToTargetBlock<T>` overloads complete your target only after every row has been delivered and the reader released (before, up to about 1,024 buffered rows could be lost with a bounded target). They no longer lose the last row when the reader fails mid-stream, and they map correctly when the reader has extra unmapped columns.
- **Connections and commands.** `OpenAsync(IDbConnection)` no longer opens a `DbConnection` twice. `EnsureOpenAsync` closes a connection that finished opening just as cancellation arrived. `FirstOrdinalResults<T>(IDbCommand, behavior)` honors `behavior`.
- **The synchronization context.** The async transaction helpers and the `ExecuteReaderAsync` overloads of the two SQL Server packages no longer resume on the caller's synchronization context: they await with `ConfigureAwait(false)`, and so does the connection open they trigger. A caller that blocked on one from a thread with a synchronization context no longer waits on that context inside the library.
- **A parameter with no value is now sent by both SQL Server packages.** It was never added to the command, so an output parameter (`AddParam(name, direction)`) never reached SQL Server. SQL Server needs a type and size for an output parameter and refuses the command without them.
- **`AddParam("name", someString)` swapped the name and the value on a compiler older than C# 13** (the .NET 8 SDK). It was found in `11.0.0-preview05` and fixed in `11.0.0-preview06`: `AddParam(string, string?)` and `AddParamIf(bool, string, string?)` use the name you write on every compiler.
- **`AddParam(name, value, dbType)` compiles again.** In the 11.0 previews a call that gave a value and a database type, such as `AddParam("@id", id, SqlDbType.Int)`, failed with an ambiguous-call error (CS0121) for an `int`, `long`, `short`, `byte` or `string` value (the `int` forms compiled in 10.1.0). New overloads with a required database type, on `AddParam` and `AddParamIf`, make every such call bind to one overload; no existing member changed.
- **A `char` is sent as the character again.** In the 11.0 previews, `AddParam("x", 'c')` bound to the `int` overload and sent the number 99; 10.1.0 sent the character. It does again.

## Earlier versions

### 10.1.0

A modernization and allocation-reduction pass. Source-compatible with 10.0: existing code recompiles cleanly.

- **Target frameworks.** `net10.0` is the primary, modern target. `netstandard2.0` and `netstandard2.1` are retained as shimmed legacy paths (.NET 8 and .NET 9 consumers use the `netstandard2.1` build). `Open.Database.Extensions.MSSqlClient` also targets `net472`. The explicit `net8.0` and `net9.0` targets were dropped.
- **Fewer allocations on the hot paths.** Case-insensitive column-to-property matching uses `StringComparer.OrdinalIgnoreCase` (and `FrozenDictionary` on `net10.0`) instead of allocating an upper-cased string per column. Assorted per-query LINQ and dead code were removed.
- **Ergonomic field-mapping overrides.** `Results<T>`, `ResultsAsync<T>`, `To<T>` and similar methods accept target-typed `new(...)` and collection expressions:

  ```cs
  cmd.Results<Person>(new("FirstName", "first_name"), new("LastName", "last_name"));
  cmd.Results<Person>([new("FirstName", "first_name"), new("LastName", "last_name")]);
  ```

  In 11, `Results<T>` and `ResultsAsync<T>` are removed: see [Coming from earlier versions](whats-new-11.md).

- **Modernized `params`.** Ordinal helpers (`Retrieve`, `AsEnumerable` and others) accept `params IEnumerable<int>` and `params IEnumerable<string>`: any enumerable, not just arrays.
- **Read-only inputs.** Several read-only `IList<T>` parameters were widened to `IReadOnlyList<T>` (`GetValuesFromOrdinals`, `EnumerateValuesFromOrdinals`, `ToDictionary`). Arrays, `List<T>`, `ImmutableArray<T>` and similar types still bind. A custom type that implements only `IList<T>`, and not also `IReadOnlyList<T>`, would need to recompile; no BCL collection is affected.
- **Lower per-query overhead.** `Transformer<T>` caches its per-type reflection once instead of rebuilding it on every query. Buffered and data-table paths pre-size collections and avoid redundant `Select` iterators.
- Fixed a wasted-allocation and incorrect-return bug in `CopyToDBNullAsNull`.
- The public API surface is tracked with `Microsoft.CodeAnalysis.PublicApiAnalyzers`, and unit-test coverage was substantially expanded.

### 9.0

- The `Open.Database.Extensions` meta-package is discontinued.
- .NET 9.0 was added to the targets so that compilation and performance improvements are available.
- Some .NET 8 and .NET 9 specific features were implemented.
- Significant cleanup and simplification where possible.

### 8.0

- All `.ConfigureAwait(true)` became `.ConfigureAwait(false)`, as they should be. A caller that needs to resume on the calling context must `.ConfigureAwait(true)` itself.
- Added `Open.Database.Extensions.MSSqlClient` for `Microsoft.Data.SqlClient` support.
- .NET 8.0 was added to the targets so that compilation and performance improvements are available.
- Improved nullable integrity.
